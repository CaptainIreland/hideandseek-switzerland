# Project context for Claude Code

An unofficial companion map for playing Jet Lag: The Game "Hide + Seek" across Switzerland. Seekers enter each answer the hider gives, and the map narrows to the area that still fits every clue.

## House rules that drive the design

1. **Google Maps is the arbiter.** Stations and places come from Google Places, and every marker links to Google Maps so a dispute can be settled on the spot. Where Google has no data (boundaries, mountains, water) the layer is labelled in the interface as not Google-verified.
2. **Built for Large games only**, following the official question pad. Small and Medium variants are not implemented.
3. **The map boundary rule.** Anything outside Switzerland does not exist for the game. Country membership is decided by Google's own address, not by testing coordinates against the outline. `SWISS_GEO` used to be a 343-point Natural Earth outline smoothed to about 500 m, wrong within roughly a kilometre of the border in both directions, which once wrongly excluded Chiasso and wrongly included Konstanz. It's now built by `scripts/fix_swiss_geo.py` from the official swisstopo `CANTONS` data plus OSM lake polygons, simplified to about 100 m, so it tracks the real border (the Rhine near Buchs SG, not a straight diagonal) and correctly excludes Campione d'Italia as an interior hole. It can still disagree with Google at the metre scale in odd spots, which is exactly why this rule exists: Google settles disputes, the outline is only ever a guide.
4. **UK English, and no em dashes anywhere**, including code comments and interface text.
5. **Stations reachable only by an excursion or charter service do not count**, because this group plays with an Interrail pass, not a GA or Swiss Travel Pass (settled on Issue #10 after `scripts/audit_private_railways.py` was first built assuming the latter). A station is excluded only if *every* line serving it is Interrail-excluded; an interchange that also carries an Interrail-covered line is left alone. This currently means: the Gornergrat, Jungfrau, Rigi, Pilatus, Brienz Rothorn and Furka-Bergstrecke cog/heritage railways, the Schynige Platte branch of Berner Oberland-Bahnen (route 68 only, not BOB's ordinary regional service), the Sihltal-Zurich-Uetliberg-Bahn's Zurich S-Bahn services (S4, S10, night SN4 - unlike the SBB/Thurbo-run S-Bahn lines in the same city, which are covered), and Swiss Rail Traffic AG Glattbrugg's charter/freight "EXT" workings (not a scheduled passenger service under any pass). It does not extend to ordinary regional narrow-gauge operators such as RhB, Matterhorn Gotthard Bahn, MOB, Zentralbahn, Appenzeller Bahnen or BOB's main network, which are Interrail-covered like the SBB network itself. See `data/private-railway-report.txt` for the full station-by-station list this produced.

## Layout

- `index.html`, `styles.css`, `app.js` load in that order. No build step, no framework.
- `app.js` has large baked data literals near the top: `CANTONS`, `MUNICIPALITIES`, `TARGETS` (places), `STATIONS_GOOGLE`. Only `TARGETS` and `STATIONS_GOOGLE` are overridden by the matching `data/*.json` files when served; `CANTONS` and `MUNICIPALITIES` are baked-only, with no `data/` counterpart. Everything else the app can show - mountains/water, districts, transit lines, high-speed lines, the full rail network, elevation - has no baked fallback at all: it is fetched from `data/*.json` only, and the corresponding UI control simply stays disabled if that fetch fails, rather than falling back to an offline copy.
- The Places tab's layers list has two rail-line toggles ("High-speed rail (in zone)" and "Other rail lines (in zone)") that draw `data/highspeed-lines.json` and `data/rail-lines.json` clipped to the current possible area (`lastRegion`, or the whole of Switzerland before any clue exists), via `clipLineToRegion()` in `app.js`. This is a visual aid, not a clue type: it does not affect `compute()`, the station viability filter, or sharing. `clipLineToRegion()` finds each line's boundary crossings with `turf.lineIntersect(line,region)` (which internally segments `region`'s rings, so it works the same for a Polygon or a MultiPolygon possible area without the `polygonToLine` Feature/FeatureCollection split `SWISS_LINE` needs), cuts the line into pieces at those crossings with `turf.lineSliceAlong`, and keeps only the pieces whose midpoint tests inside the region. Each segment is drawn twice, a wider dark `RAIL_CASING` (`#14202e`) line first and the coloured line on top - a thin line with no casing visually disappeared into whichever OSM tile colour happened to match it, the same problem markers avoid with their white stroke in `render()`, just inverted since the basemap here is uniformly pale.
- **Marker and line colours are chosen against the live OSM basemap, not eyeballed.** `CATS`, `COLOR.station` and `RAIL_COLOR` (`app.js`, near the top) were picked by porting `validate_palette.js`'s OKLCH/OKLab/CVD-simulation maths to Python (this machine has no Node runtime) and checking each candidate's WCAG contrast against representative OSM tile swatches (park green, water blue, urban tan, road orange) plus pairwise CVD separation (Machado-Oliveira-Fernandes protan/deutan simulation) against every other category. `station` (`#e30613`) is deliberately unchanged - it is reused as `var(--red)` across buttons, the possible-area outline and hiding zones, out of scope for a marker-colour pass. With 13 simultaneously-toggleable categories plus station, perfect pairwise separation is not achievable (the skill's own validator can't pass 8 categories at its target threshold under an all-pairs check); several pairs remain below the recommended separation floor after this pass and are mitigated only by the text label every marker already carries in the layers list and its popup, not by colour alone.
- Leaflet draws, Turf.js does the geometry. Both are vendored in `vendor/` (pinned versions: Leaflet 1.9.4, Turf.js 6.5.0) so the app loads with no internet connection; `index.html` falls back to cdnjs only if the local copy is missing.
- There is no in-app Google key or live-data fetch. Every player works off the same committed `data/*.json`, produced offline by the pipeline below, so nobody's map can silently drift onto a different dataset mid-game.

## Data pipeline

Run from the repository root. Only the first two cost money.

```sh
python scripts/fetch_stations_google.py YOUR_KEY   # writes data/stations.json
python scripts/fetch_places_google.py YOUR_KEY     # writes data/places-raw.json
python scripts/filter_places.py                    # raw -> data/places.json, free, re-run freely
python scripts/fetch_osm_layers.py                 # writes data/osm-layers.json, free, no key
```

The sweep scripts walk Switzerland in adaptive square cells, subdividing wherever Google's 20-result cap is hit. A key used for scripts must have its application restriction set to None, because a key locked to a website rejects calls made outside a browser. Use a second key for that and keep it out of the repository.

`filter_places.py` is deliberately separate from the sweep so thresholds can be tuned without paying again. `MIN_REVIEWS` at the top of that file is the main dial. Review count turned out to be the only strong signal for whether a place is the real thing: Google's primary type for a dental surgery is genuinely `hospital`, so type filtering alone barely helped.

`scripts/fix_swiss_geo.py` is a separate, one-off data-repair script, not part of the sweep above: it rebuilds the baked `SWISS_GEO` literal in `app.js` from the `CANTONS` literal plus the `waters` in `data/osm-layers.json`, needs `pip install -r scripts/requirements.txt` (shapely, pyproj - the only non-stdlib Python dependency in the repo, scoped to this one script), and writes a `data/swiss-outline-report.txt` audit trail. Re-run it if `data/osm-layers.json`'s water list changes (for example after re-running `fetch_osm_layers.py`).

`scripts/audit_private_railways.py` is another one-off, read-only script: it cross-references `data/stations.json` against `data/transit-lines.json`'s GTFS-derived agency/route data to flag stations served only by an excursion or charter operator (house rule 5 above), writing `data/private-railway-report.txt`. It does not modify station data itself; any removal it suggests is applied by hand afterwards. Re-run it after a fresh `fetch_stations_google.py` or `fetch_transit_lines.py` sweep to check nothing excursion-only has crept back in.

A few more free, no-key scripts feed the non-Google layers used by matching and measuring: `scripts/fetch_districts.py` writes `data/districts.json` from OpenStreetMap (swissBOUNDARIES3D's export carries cantons and municipalities but not districts) and switches on the district and district-border questions; `scripts/fetch_elevation.py` writes the swisstopo elevation grid to `data/elevation.json`; `scripts/fetch_transit_lines.py` writes the GTFS-derived `data/transit-lines.json` that both `audit_private_railways.py` and the transit-line matching question depend on; `scripts/fetch_highspeed.py` writes `data/highspeed-lines.json` (see Question semantics above) from an Overpass query of OpenStreetMap rail geometry. `scripts/fetch_stations.py` is a separate, OSM-based alternative to `fetch_stations_google.py`'s strict-Google sweep, kept for comparison rather than as part of the normal pipeline.

`scripts/fetch_rail_lines.py` writes `data/rail-lines.json`, a companion to `fetch_highspeed.py` reusing that script's Overpass-fetch/merge/RDP-simplify machinery, but with no speed filter and covering both `railway=rail` and `railway=narrow_gauge`, for the "Other rail lines (in zone)" map toggle (see Layout above). It exists because `data/transit-lines.json` was the first thing tried for that toggle - it already carries GTFS agency/line-code identity - but the official Swiss GTFS feed turns out to have no `shapes.txt` and no `shape_id` column on `trips.txt`, so it has no route geometry to give, only station-name sequences; OSM is the only source of real track paths available here. The trade-off is losing GTFS's named-line identity: lines in `data/rail-lines.json` are anonymous merged OSM way chains (occasionally OSM's own `name` tag survives), not "S3" or "IC1". It also has no equivalent of house rule 5's excursion/charter-only exclusion, since that list was built by cross-referencing GTFS route data against `data/stations.json`, which does not carry over to OSM way geometry - a heritage line like the Gornergrat is drawn on the map here even though its stations are excluded elsewhere. Accepted as a gap (see Known gaps below) since this is a visual aid, not a clue type or a change to station eligibility.

## Question semantics, taken from the rulebook

- **Radar**: hit keeps the circle, miss cuts it. Radar asks about the hider's location, not their hiding zone.
- **Thermometer**: half-plane on the perpendicular bisector, toward the end point when hotter. Each thermometer question has a minimum distance the asker must have travelled for the answer to be valid (½/3/10/50 mi or 1/5/15/75 km), tracked as `THERMO_QUESTION_KM` and compared live against the actual straight-line `turf.distance()` between the two points. Falling short only warns, never blocks, since the geometry is valid either way; the measured distance and any shortfall are baked into the clue's label so a mixed-compliance history stays legible.
- **Matching**: Voronoi cell of the asker's nearest thing, or containment for canton and municipality.
- **Measuring**: union of discs of radius equal to the asker's own distance, around every candidate. For border, water, canton border, district border and high-speed rail line references it is a band around the boundary instead. High-speed rail is qualified per OpenStreetMap track segment, not as a hand-picked list of named lines: any `railway=rail` way tagged `highspeed=yes`, or carrying a `maxspeed` (including direction-specific `maxspeed:forward`/`maxspeed:backward` and semicolon-separated multi-values) of 200 km/h or more, counts, since speed can change partway along a named line (the Solothurn-Wanzwil line runs at 140 km/h from Solothurn to Subingen and only reaches 200 km/h after that, so only the faster stretch counts). `scripts/fetch_highspeed.py` fetches qualifying ways from Overpass and merges touching ones into continuous lines, writing `data/highspeed-lines.json` and an audit trail at `data/highspeed-report.txt`; re-run it if the OSM data changes or the threshold (`RAIL_MIN_KMH`) is retuned. Elevation is different again: the asker's own elevation is looked up from `data/elevation.json` (a ~1 km swisstopo grid, rounded to the nearest 50 m per house ruling), then `turf.isobands` builds the contour polygon for everywhere at or above that elevation; higher keeps it, lower cuts it. This is the only clue type built on a raster grid rather than vector polygons or lines.
- **Tentacles**: the radius is measured **from the asker**, and only places inside that radius are candidates. Naming a place keeps the part of the asker's disc nearest that place. "Not in range" removes the whole disc. Official radii are one mile (2 km) for museums, libraries, movie theatres and hospitals, and fifteen miles (25 km) for zoos, aquariums and amusement parks. Train stations are not a tentacle category.
- **Station identified** is not one of the five rulebook questions; it is the strongest possible clue, built as an ordinary clue type (`buildStationClue()`) rather than a separate mode so it gets sharing, editing and the viability filter for free. Its polygon is a circle at the confirmed station using whatever the hiding-zone radius is *at the moment it is built* (add time, edit time, or replay time), not a value frozen into the share code, because the radius is meant to track the shared `z` setting rather than be independent of it. The same Station tool can instead manually rule out stations still in play through a searchable multi-select checkbox list. One submission creates a separate `station-block` clue for each selected station, so every ruling can still be toggled, edited or removed independently. A `station-block` clue has no fixed polygon: `applyStationBlocks()` dynamically subtracts the union covered only by active ruled-out stations while preserving every overlap covered by at least one viable, unblocked station. Each ruled-out station is also removed from the viability set even when one of those protected overlaps remains.

Clue geometry is frozen when a clue is added, so later data changes never silently rewrite an existing clue. The deliberate exception is `station-block`, whose exclusion must be recalculated as other stations are ruled out, restored or made non-viable so shared hiding-zone overlaps remain correct. Each clue also has a quick effect toggle: hiding its effect excludes it from `compute()` without deleting it, and showing it restores the same geometry or station ruling. The toggle replaces the clue object rather than mutating it so the reference-based compute cache invalidates correctly. Its state is saved locally, preserved through editing, and included in share format v5. An existing clue can be edited (pencil icon in the clue list): `startEdit()` repopulates the right tool's form from `clue.share`, including restoring the unit it was created in, and sets `editingIndex` so the next commit replaces `clues[editingIndex]` in place instead of appending. Removing, cancelling or clearing all clues always resets `editingIndex` (adjusting it down, not just clearing it, when an earlier clue is removed while a later one is being edited), otherwise a later update silently writes into the wrong slot.

The corner location control has separate tracking and recenter buttons. Tracking uses Leaflet's continuous `watch:true` mode with `setView:false`, so the blue position and accuracy ring update without moving the map; recentering happens only through the explicit second button. The "Me" buttons next to each Pick button copy the latest tracked fix into that coordinate pair without changing it again as the player moves. If no fix exists yet, a `mePending` flag records which pair is waiting and starts tracking; the first shared `locationfound` event fills it. A fix worse than about 100 m warns but does not block, since a radar centre off by that much materially changes the possible area.

Every paired latitude/longitude control accepts a complete comma-separated coordinate pasted into either input, for example `46.872874, 9.882280`. Valid latitude and longitude ranges are checked before both fields are replaced; a normal single-value paste is left to the browser.

The dark mask always shows Switzerland as the play area, even before the first clue: with no clues it shades world-minus-Switzerland, and only switches to world-minus-possible-region once a clue exists (the red outline stays clue-only, since with none it would just retrace the border). `WORLD_MASK` is deliberately wide (roughly +/-179 longitude, +/-85 latitude) so the grey does not run out a few zoom levels out; keep it short of the antimeridian and the poles, since a polygon touching either makes Turf's boolean ops misbehave.

**Imperial and metric are parallel rule sets, not conversions.** The Large-game question pad has two official value sets (10 mi radar and 15 km radar are different questions, not the same distance in two units), all in `UNIT_TABLE` in `app.js`. Whichever member is selected is converted exactly to kilometres for geometry, so a 1/2 mi thermometer requires 0.804672 km while its paired metric question requires 1 km. The units toggle in the panel header (visible from both tabs) switches which preset values the preset buttons, the tentacle auto-fill and the hiding-zone selector show, and what unit typed distances and readouts use, but it never touches an existing clue: each clue's label is baked in at add time from whatever unit was active then (`clue.share.unit`), and stays that way regardless of later toggling, exactly like frozen geometry above. Internally every distance is a plain kilometre number (`toKm()`/`fromKm()` convert only at the form fields and the `fmtDist()`/`fmtArea()` readouts); `circle()` and `withinOf()` both take kilometres directly. Toggling units with clues already on the map shows a banner warning that existing clues keep the distances they were created with.

**Sharing a map state.** "Share this map" encodes the clue list into the URL hash (`#v=5&z=<zone km>&r=<min reviews>&f=<stations>.<places>&c=<clue>~<clue>...`), never the query string, so it never hits a server. The hash stores each clue's original inputs (coordinates to 5dp, distances as canonical kilometres) and whether its effect is currently shown, not its frozen geometry. Replay rebuilds every clue through the same `buildRadarClue()`/`buildThermoClue()`/etc. functions the "Add clue" buttons call, so a shared link always reflects whatever `clip()`/`circle()`/voronoi logic the recipient's build actually runs. Distance-bearing clues also carry the sender's creation unit, used only to keep the replayed label reading the way the sender saw it; the thermometer's `T` clue additionally carries its minimum-distance requirement (`questionKm`) so a mixed-unit history still shows the right shortfall warning on replay. A named tentacle place, an identified station (`P|lat|lng`), or a ruled-out station (`B|lat|lng`) resolves by nearest coordinate, not by name, since a recipient's dataset may differ slightly. `f` is a fingerprint (station count, place count); a mismatch against the recipient's own counts shows a prominent banner, since the two sides may then disagree on answers. Clues that fail to parse or whose category has no data are dropped and the drop count is reported, never silently shortened. Replay waits for `loadStations()`, `loadPlaces()` and `loadOsm()` to settle before touching the hash, since match/measure/tentacle clues and the fingerprint all depend on that data. `SHARE_VERSION` bumps whenever the wire format changes incompatibly (most recently to 5, for manually ruled-out stations); old links just show a graceful "this build does not understand that format" banner rather than misparsing.

## Performance traps already hit

- Buffering detailed border lines by tens of kilometres took over three minutes. The canton border band instead erodes each canton and subtracts, which takes about a second. Do not reintroduce line buffering at scale.
- `turf.polygonToLine` returns a Feature for a Polygon but a FeatureCollection for a MultiPolygon. Handling only the first form silently dropped every canton with an exclave.
- The station viability filter recomputes after every clue and hides stations whose hiding zone no longer overlaps the possible area, plus stations named by active `station-block` clues. Keep it bounding-box gated.

## Known gaps

- **Airports are manually audited against Google Flights** (`data/airport-audit-report.txt`, last checked 2026-08-06): of the 17 entries that pass the 100-review proxy, 5 have flights displayed to or from the airport (Bern, Geneva, Sion, St. Gallen-Altenrhein and Zurich). Seasonal and charter flights count because the rule is only whether Google Flights displays a flight, not how the airline classifies its service. The result is persisted in `GOOGLE_FLIGHTS_AIRPORTS` in `scripts/filter_places.py`, and is applied after the existing type and review filters, so rerunning the filter preserves both requirements. There is no Google Flights API in this pipeline, so update that set by hand after a fresh Places sweep.
- **Coastline and landmass** return null answers in Switzerland by the rulebook's own definitions (it is landlocked). Documented, not implemented. **Sea level / altitude is implemented** (see the Measuring "Elevation" reference below) - the rulebook's own warning that phone altitude readings are unreliable does not apply here, since the asker's elevation is looked up from the same grid as the hider's, never read off a device.
- **Hospital coverage is slightly incomplete in a few city centres**, where the sweep hit its subdivision floor.
- Three stations Google does not list (Faulensee, Trübbach, Weite) are absent under the strict rule.
- **Transit line matching misses heritage and rack railways** (Pilatus Kulm, Brienzer Rothorn, the Furka steam line, and similar), because Google often does not type their termini as `train_station`, so they are absent from `data/stations.json` and cannot be matched against the GTFS feed. Accepted as a gap rather than chased down, since these lines typically need a supplement beyond a standard rail pass and the group would not ride them anyway. See `data/transit-lines-report.txt` for the full list of unmatched-but-nearby GTFS stop names this surfaced.
- **`SWISS_GEO` has about 6 km2 of small stray gaps** (a few dozen fragments, largest under 2 km2) along the Bodensee shore, where the swisstopo canton edge and the OSM lake polygon disagree near the diplomatically undefined Swiss/German/Austrian line in the lake. `fix_swiss_geo.py` fills these rather than leaving odd-shaped holes in open water, since none of them are an intentional exclusion (only Campione d'Italia is) - accepted as noise at the 0.01% level rather than chased to the metre on a line international law itself doesn't fix.
- **`data/rail-lines.json`'s lines are anonymous and unfiltered by house rule 5.** Unlike `data/transit-lines.json`, OSM way geometry carries no GTFS agency/route identity, so the "Other rail lines (in zone)" map toggle cannot label a line "S3" or exclude excursion/charter-only track (Gornergrat, Jungfrau, Rigi, Pilatus, Brienz Rothorn, Furka-Bergstrecke, the Schynige Platte branch) the way `data/stations.json` does. See `scripts/fetch_rail_lines.py`'s docstring. Accepted as a gap since this is a visual aid, not a clue type.

## Testing

There is no test runner. Geometry changes were validated by evaluating `app.js` in Node with real `@turf/turf` and stub `document`/`L` objects, then asserting on areas, containment and timings. Area conservation is the strongest check available: clipping the same region with a clue and its inverse should sum to Switzerland's area (about 41,285 km2, since the `fix_swiss_geo.py` rebuild - previously 41,425 km2 under the old Natural Earth outline, per `data/swiss-outline-report.txt`) within a couple of percent.

Browser behaviour cannot be verified from a sandbox, so interface changes need a human to open the page. A CSS rule once made `hidden` ineffective on the tool forms and every form rendered at once, which no amount of static checking caught.
